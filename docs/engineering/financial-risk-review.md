# Financial risk review: reconciliation

Status: reviewed 2026-11-25. Six risks raised earlier were checked against the code. A risk is **confirmed** only when a test failed on the code as it was; everything else is **hypothetical** (or not a defect) and is pinned by a test so it stays that way. Tests are in `backend/tests/test_financial_risks.py` unless named.

| # | Risk | Finding | Confirmed / hypothetical | Fix | Test |
|---|---|---|---|---|---|
| 1a | Supplier invoice line lists a ticket delivered outside the line's dates | Reported: the row is *outside this invoice line* with "delivered YYYY-MM-DD", the line is a discrepancy, and the ticket's tons and dollars are a ticket-level effect. Approved totals count only deliveries inside the dates, and the dollar effects add up to the line's difference to the cent. | Not a defect | None | `test_a_supplier_line_listing_a_ticket_delivered_after_its_dates_reports_it_and_adds_up_exactly` |

## Measurements (risk 6)

How it was measured: `scratchpad/measure_reconciliation.py`, which reuses `backend/scripts/measure_performance.py` (`generate`, `one_request`). It builds a temporary SQLite database on fictional data, then times one request per fresh process. The data was 20,000 tickets (2,605 with a per-ton hauler charge), 2,000 approved shifts (one in ten split 6/3 across two projects), 300 supplier invoice lines listing 6,000 tickets, and 100 hauler invoices with 2,000 lines (hours and per-ton). Times come from a shared development Mac with other work running. They varied by up to 2× between runs, so read them as rough sizes. The SQL statement counts are exact.

| Request | Before: seconds, SQL | After: seconds, SQL | Response |
|---|---|---|---|
| `/api/invoice-comparisons` | 0.78 s, 86 | 1.1–1.3 s, 86 | 4.3 MB |
| `/api/invoice-comparisons?summary=true` | 0.59 s, 86 | 0.8–2.0 s, 86 | 0.43 MB |
| `/api/hauling-invoices` | 0.57 s, **110** | 0.63–0.82 s, **11** | 0.68 MB |
| `/api/exceptions` | 2.3 s, 101 | 2.3–3.9 s, 101 | 9.4 MB |
| `/api/invoice-comparisons/register` | 1.22 s, **197** | 1.20–1.22 s, **98** | 0.14 MB |

The exceptions list is the slowest request, and it returns 9.4 MB. Its statement count doesn't grow with the number of invoices. Its time goes into recomputing every line and serializing the response, not into an N+1 or a quadratic loop, so it wasn't changed. If it grows, the first step is paging or a summary mode like the invoice list has. The split-shift fix avoids quadratic lookups: repeat checks and *not billed yet* use dictionary or set lookups per shift.

## Not changed, worth knowing

- `haul_billing.py` (a ticket's hauling reason, "the shift pays for it"), the review form's "paid by its hourly truck shift" and the welcome page's "before you pay" are outside this review's files. The review form's wording could follow the same change.
- An hours, standby or minimum line dated outside its own invoice's period isn't questioned. Only listed deliveries on per-ton and per-load lines are.
- A per-ton line that lists the same ticket number twice counts it once. The extra quantity then shows as *quantity hauled differs* with its dollars, not as a repeat.
